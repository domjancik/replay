# reMarkable renderer landscape

*Primary documentation reviewed November 13, 2026. Project capabilities below come from the cited docs, release records and source descriptions. The numerical results in the calibration article are rm-redraw version comparisons against specific official exports. This survey includes no shared-input competitor timings or image scores.*

## The export paths set different targets

reMarkable's desktop app officially exports PDF, PNG and SVG. For the evaluated firmware and desktop app, rm-redraw found the desktop app PNG and rasterized USB PDF of the same portrait had materially different local shading. The desktop PNG is the comparison target for app-like raster texture. A PDF with a named rasterizer is a separate target for print/export appearance, geometry and supported paint operators. The tablet display itself adds a third target if the goal is appearance on-device. [Official desktop export documentation](https://support.remarkable.com/articles/Knowledge/Desktop-app) · [Calibration evidence](calibration-journey.md#5-the-export-target-changes-the-answer)

## General brush engines

Krita's brush texture settings separate pattern scale, offsets, alpha and lightness. Its documented texture modes can simulate holes and different ways of applying texture strength. `libmypaint` exposes brush settings driven by pressure, multiple speed estimates, and stylus tilt. These are relevant models for brush design. A reMarkable replay still has to map the saved channels to observed appearance using a paired export. The physical worksheets in rm-redraw support a recorded-width contribution from tilt and leave the stored-direction mapping unresolved. [Krita texture settings](https://docs.krita.org/en/reference_manual/brushes/brush_settings/texture.html) · [MyPaint inputs in Krita](https://docs.krita.org/en/reference_manual/brushes/brush_engines/mypaint_engine.html) · [libmypaint brush settings](https://github.com/mypaint/libmypaint/blob/master/brushsettings.json)

## What rm-redraw contributes

The distinctive deliverable is an offline path from saved ink through deterministic progressive reveal to cropped, loopable video, backed by explicit geometry and reference provenance. The calibration trail includes split control sets, regressions and an isolated compositing experiment. The same rendering path serves static and progressive output. The opt-in Rust deposition kernel was checked for exact Python output on the reported workloads. Natural portrait results improved most clearly in local darkness, and tool behavior and pixel fidelity remain incomplete. The implementation needs paired native evidence for its supported automatic text-anchor path. [Calibration journey](calibration-journey.md) · [Replay and renderer contracts](contracts.md)

## A controlled renderer comparison

A defensible comparison would pin each revision and renderer backend, then feed every candidate the same shareable raw pages. Include isolated simple pens, controlled pressure/width/angle, one/three/nine overdraw, erasers and a mixed-layer natural page. Keep both desktop PNG and USB PDF targets with firmware, app and rasterizer versions, raw-member hashes, dimensions, color handling and crop. Compare full-source images and explicitly area-reduced previews. Record unsupported tools or document features beside each result.

For simple ink, report edge distance, stroke widths, cap shapes and palette values. For textured ink, report support, density, ink mass, local contrast, spatial correlation and pixel residuals at both scales. Keep any parameter fitting separate from fresh reserved controls. Measure static and replay workloads separately on one machine with pinned versions, repeat runs, memory and warm/cold distinctions. A replay comparison also needs fixed viewport, unchanged visible prefixes, layer/eraser behavior, timing provenance and final lossless frame equality against each candidate's own static result. This design would establish where each implementation leads for a specific target and workload.
